## 1. 赛制事实（2026-10-16 官方 /docs/api、/rules 全文核实）

1. 参评系统只提供 Add / Search；Answer（冻结模型）、Eval（测试执行）、编排全部平台侧。
2. Top K = 100；返回条数**不得超 top_k（可少于）**；Answer 输入预算 **117,760 tokens，按返回顺序保留前缀**。
3. **单次请求最长 30 分钟**；Add 内部异步允许但端点须等处理完成再回 200；官方异步通道 = 202 + 预绑定 `{task_id}` 状态地址（不用，采用同步）。
4. Add 同 request_id 有界重试最多 32 次；`(user_id, request_id)` 幂等必须。
5. 评测形态：**300 个一次性隔离域**（每域 ≈5 次 Add + 1 次 Search，user_id 强制隔离；域内跨 Add 合法，跨域永不）。
6. **合规边界**：Search 只禁"生成最终答案 / 答案伪装成记忆"；`content` 仅要求非空字符串，平台原样转传；"你的系统负责持久化、组织、索引和更新记忆"——**Add 侧 LLM 蒸馏合法**；评测数据"派生副本"明示允许（限任务使用、30 天删除）。
7. 商业榜：无 Add/Search 模型限制；不参与奖金；新申请签发新 Eval Key；smoke 1 次/小时（每赛道 ≤30）；full 每 Key 每赛道 2 次、第 2 次须首次完成后 30 天。
8. 正式评测版本冻结：full 受理后代码/镜像/API 与申报版本一致。

**57.67 分项诊断**（设计依据）：
- file localized 90.7/92.7 vs resolved 56.67/58.67 —— **两条件都恰差 34 分：检索找到证据，answer 用不起来 = 内容形态瓶颈（P0）**
- bug fix 52.53（两条件相同）vs new feature 64.71/70.59 —— bug 靠推理链、feature 靠上下文
- 噪声分级 L1 90.0 / L2 55.6 / L3 12.5 / L4 59.4 —— L3 = 同仓近邻干扰（词面相似、语义无关），排序层盲区
- 本地 HitRate@100 = 96.4%，MRR 0.67→0.744（rerank 后）—— 召回已解决

## 2. 架构总览

**换心脏不换骨架**：

- 保留（v0.4 骨架）：FastAPI 契约端点、`(user_id, request_id)` 幂等、代码感知分词、BM25+dense+RRF+门控检索、邻接扩展、部署链路、本地评测脚本
- 新增（v1 心脏）：
  - **Add 侧同步蒸馏管道**（经验卡生成 + Pass-2 校验 + 域内合并）
  - **Search 侧强模型判别 + 题型条件化打包**（token 预算内证据组装）
  - **本地 answer 仿真闭环**（G1-G4 门禁，开发期唯一真反馈）

```
平台 Add ──→ 幂等登记 ──→ 原块落盘+索引(现有) ──→ 蒸馏 Pass1(强模型,1~N卡)
                                                    │
                                        Pass2 事实校验(文件/行号/命令回溯原文)
                                                    │不合格→ 丢弃留原块
                                        卡落盘+双索引 + repo概览卡增量合并
                                                    │
                                                回 200                                ← 全程同步，单请求 30min 余量
平台 Search ──→ 双路召回(卡加权) ──→ 强模型判别(三分类+题型识别) ──→ 条件化打包 ──→ 返回 20~100 条
                  (原块路径不动)        (query+options 联合)         (预算内选/排/裁)
```

## 3. 记忆卡设计

### 3.1 DEBUG 卡（bug fix 型经验）

```
[TASK] <一句话：什么仓库/模块的什么 bug>
[SYMPTOM] <可检索的症状描述：报错文本、失败测试、触发条件>
[ROOT_CAUSE] <根因一句话，说人话>
[FIX] <修法：改哪个函数、怎么改、关键代码意图（不是 diff 全文）>
[FILES] <file:line 列表，与 gold patch 对应的改动点>
[VERIFY] <可执行验证命令>
[WHEN] <时间基线：该经验对应的仓库状态（PR/commit 日期）>
```

### 3.2 PATTERN 卡（feature/架构型经验）

```
[TASK] <实现了什么功能/重构>
[PATTERN] <采用的架构与代码组织方式、遵循的惯例>
[FILES] <涉及文件及角色>
[API] <暴露/使用的接口约定>
[VERIFY] <验证方式>
[WHEN] <时间基线>
```

### 3.3 repo 概览卡（每域一张，增量合并）

```
[REPO] <仓库定位/语言/框架/目录结构要点>
[CONVENTIONS] <编码与测试惯例>
[TEST] <测试命令与入口>
[UPDATE_LOG] <增量合并时间线>
```

### 3.4 生成规则

- 1 次 Add → 0~3 张卡（按轨迹内独立问题数拆分）；卡 150~400 tokens，英文，自足无代词歧义
- **处方化原则**：写给能力中等的同事看的交接笔记，零推理跳跃
- 所有 FILES/VERIFY 字段必须可回溯到源文本（Pass-2 自动校验，不可回溯 → 卡丢弃、原块保留）
- 原块永不删除：卡是新增语料，原块是回退证据与词面检索锚点

## 4. Add 管道（同步蒸馏）

```
POST /add
 1. (user_id, request_id) 幂等检查（现有逻辑不动）
 2. 原块分块/分词/嵌入/落盘（现有 v0.4 路径，不动）── 毫秒级
 3. 蒸馏 Pass 1：messages → 草稿卡（强模型，JSON schema 约束，temperature 0）
 4. Pass 2 校验：卡字段回溯源文本匹配；失败 → 单次重生成；再失败 → 丢弃留原块
 5. 卡落盘 + 卡文本双索引（BM25+dense，卡与原块同库不同类型标记）
 6. repo 概览卡增量合并（域内第 N 次 Add 后重合并，幂等可重做）
 7. 回 200
```

**失败降级矩阵**：

| 故障 | 行为 |
|---|---|
| 蒸馏超时（单 add 预算 ≤90s 硬顶） | 放弃蒸馏，原块照常，回 200 |
| Pass-2 校验两次失败 | 该卡丢弃，原块保留 |
| OpenRouter 429/5xx | 有界重试（≤2 次，指数退避）；超限走降级 |
| 平台 Add 重试（同 request_id） | 幂等命中直接返回 |

**并发预算**：平台 Add 并发 16-64 → 蒸馏并发对齐（OpenRouter 并发 32+），1465 次 add 蒸馏墙钟目标 <1.5 小时（远小于平台灌入+排队的实际节奏）。

## 5. Search 管道（判别 + 条件化打包）

```
POST /search (query + options + user_id + top_k≤100)
 1. 双路召回（现有 BM25+dense+RRF）：卡与原块同池，卡乘 boost（默认 1.3，消融定值）
 2. 强模型判别（listwise，query+options 联合）：
    - 题型识别：bug-fix 型 / feature 型 / 其他
    - 三分类：ACTIONABLE / CONTEXT / IRRELEVANT
    - 显式规则："同仓库但解决另一问题 = IRRELEVANT"（L3 解药）
    - 保守偏置：拿不准判 CONTEXT 不判 IRRELEVANT
 3. 题型条件化打包：
    - bug 型：repo 概览卡 → DEBUG 卡（按置信度）→ 卡的原文摘录配对 → 收紧（30~50 条）
    - feature 型：repo 概览卡 → PATTERN 卡 → 更宽的 CONTEXT/原块（60~90 条，保住"宽上下文供分"效应）
 4. 预算裁剪：总 content ≤55k tokens（给长 problem_statement 留余量）；超预算按序截断
 5. 返回（≤top_k；判别/LLM 全失败 → 回退 RRF 原序前 100）
```

**合规红线**：Search 侧 LLM 输出只影响排序与筛选决策；返回的每条 content 都是已存储记录，**零现场生成**。

## 6. 本地 answer 仿真闭环（G1-G4 门禁）

### 6.1 仿真架构

- 数据：SWEContextBench（Experience 1007 / Related 362 / Relationship / Lite，本地 parquet）
- 噪声复现：沿用 eval_noise.py 方法论构造 L1-L4 分级（L3 = 同仓近邻任务干扰，重点复现）
- answer 仿真：固定模型（候选 gpt-4o / claude-sonnet 两档交叉），输入 = 题目 + 我们 Search 返回的记忆，输出 patch
- 判分：SWEContextBench-eval（SWE-bench harness，docker，FAIL_TO_PASS/PASS_TO_PASS）

### 6.2 评测子集

- 分层抽样 80~100 题：bug:feature ≈ 2:1，覆盖 12 仓，relevant/noisy 两条件
- **固定子集**：所有配置跑同一批题（配对比较，消任务难度噪声）

### 6.3 消融与门禁（防震荡协议核心）

组件单独 → 组合归因：

```
baseline(v0.4) → +卡 → +卡+判别 → +卡+判别+打包(全量)
```

**G1 检索回归**：HitRate@100 ≥96%、MRR 不降（现有脚本，防退化护栏）
**G2 卡质量**：字段可回溯率 ≥95%（Pass-2 日志自动统计 + 抽样 50 张人审）
**G3 端到端（主闸门）**：同题配对 A/B，
- 全量配置总分 +9~12pp（相对 baseline）
- bug 子集 +12pp；L3 复现集 12.5 → ≥55
- **分片不回退：任何 n≥30 切片（题型×条件×噪声级×仓）回落 ≤2pp**
**G4 稳健性**：2 蒸馏 prompt 变体 × 2 判别模型，四格全为正；leave-one-repo-out 抽查不翻负

**出手规则：G1-G4 全绿才提交 full；G3 落在 +5~9 区间 → 按打平/逼近 top1 预期提交并接受；<+5 → 不烧 full，继续迭代。**
